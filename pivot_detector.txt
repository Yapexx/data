## Research objective

The ultimate objective is NOT to predict when the ZigZag finally confirms a pivot.

A ZigZag extreme occurs at an earlier bar `t*` and is only confirmed later at `t_c`.

What we want to investigate is:

> Using only information causally available at the close of bar `t`, can we estimate the probability that this exact bar `t` will later be identified as the true pivot bar `t*`?

The motivation is to identify probable exhaustion / turning points as early as possible, ideally on or close to the actual extreme, rather than waiting for ZigZag confirmation.

The ZigZag therefore has two roles:

1. maintain causal market/leg state and generate per-bar features;
2. retrospectively identify `t*` bars that can be used as supervised-learning labels.

Do NOT use the confirmation bar `t_c` as the positive target unless we explicitly decide to investigate that as a separate experiment.

## Important causal/state convention

The current design intentionally computes a bar's predictive features BEFORE applying any pivot that becomes confirmed on that same bar.

So on confirmation bar `t_c`:

* features returned for `t_c` must represent the state that was known before the pivot transition;
* `mark_pivot()` is applied afterwards;
* the updated pivot/macro/micro state is stored for subsequent bars;
* historical rows are never recomputed.

This is deliberate because the ML inputs for a bar must not contain information derived from a pivot confirmation that only became known after evaluating that bar.

Please audit that this invariant is actually respected everywhere in the current implementation.

## Recent issue to verify carefully

We were revisiting `leg_inefficiency`.

The intended conceptual metric is:

```
efficiency = straight displacement / total travelled path
inefficiency = 1 - efficiency
```

Both numerator and denominator MUST use the same origin.

We had concluded that if the geometric leg origin is the actual pivot extreme, then total path must also start at that pivot extreme rather than starting from an unrelated previous close.

Please inspect the CURRENT implementation and determine whether this has been correctly resolved. Do not blindly implement the previous suggestion if the existing code now differs.

More generally, audit every stateful feature for:

* reset timing;
* origin consistency;
* behaviour immediately after confirmation;
* behaviour on `t* -> t_c`;
* accidental negative/out-of-range values;
* stale state carried into a new leg.

## Pivot labels

The planned first label is binary:

```
is_pivot[t] = 1 if bar t was later confirmed by the ZigZag as the actual pivot location t*
              0 otherwise
```

The confirmation bar itself should not receive the positive label unless it is coincidentally also the true pivot location.

We previously observed roughly 309 pivots in about 5,000 bars after adjusting pivot-separation logic, which is enough for an exploratory Random Forest baseline but still small enough that validation methodology matters.

Please verify the actual current count from the data rather than relying on that historical number.

High and low pivots may eventually be:

* one binary target (`is_pivot`), with direction/context as features; or
* two separate targets/models (`is_high_pivot`, `is_low_pivot`).

Challenge which formulation is preferable.

## Critical research question

Do NOT assume that predicting the exact ZigZag pivot is necessarily the economically best target.

The ZigZag label depends on configurable thresholds, so a model may simply learn the behaviour of that particular detector.

As part of the research design, compare or at least propose alternatives such as:

1. exact ZigZag pivot `t*`;
2. pivot within ±N bars;
3. bar followed by a reversal of at least X ATR before continuation of Y ATR;
4. probability of a meaningful reversal within N bars;
5. separate continuation-vs-reversal outcome from the current running extreme;
6. high-pivot and low-pivot models separately.

The existing pivot scenario code contains MFE/MAE, ATR-normalized excursions and time-to-target machinery which may be reusable for these alternative economic labels.

## Proposed research sequence

I want you first to inspect and critique the existing implementation, then propose the smallest clean research pipeline.

Preferred sequence:

### Phase 1 — correctness audit

Audit:

* exact `t*` versus `t_c` semantics;
* pivot label generation;
* ordering in `ZigZagATR.update()`;
* all feature reset/update timing;
* macro/micro state timing;
* candidate/run-extreme handling;
* retracement calculations;
* leg inefficiency;
* any feature leakage;
* any raw price/time variables that should instead be transformed or normalized.

Do not modify production code unless there is a clear correctness issue.

### Phase 2 — dataset

Create or propose a generic dataset builder where:

* one row = one completed bar;
* X = only information available at that bar;
* y = eventual pivot label for that same bar;
* metadata such as timestamp, pivot confirmation time etc. is retained separately and never accidentally used as model input;
* categorical and numerical feature definitions are explicit.

Prefer generic/reusable code rather than hard-coding BTC or one timeframe.

### Phase 3 — descriptive feature research

Before Random Forest:

* report target prevalence;
* analyse each feature with the existing FeatureEvaluator;
* examine distributions on pivot vs non-pivot bars;
* inspect monotonicity;
* inspect highly correlated/redundant features;
* test stability through time;
* compare high and low pivots;
* identify suspiciously powerful features that may indicate leakage.

### Phase 4 — baseline ML

Only after Phase 1–3:

* build a Random Forest baseline;
* use chronological / walk-forward validation, NOT a random train/test split;
* account for class imbalance;
* report precision, recall, PR-AUC and probability calibration;
* include a simple baseline comparison;
* inspect permutation importance rather than relying only on impurity importance;
* optionally use SHAP later, but keep the first implementation simple.

The purpose of the first RF is NOT parameter optimisation. It is to answer:

> Is there real out-of-sample information in these features about future identification of the current bar as a pivot?

### Phase 5 — trading relevance

If exact-pivot prediction shows signal, investigate whether probability buckets correspond to useful forward:

* return;
* MFE;
* MAE;
* time-to-reversal;
* risk/reward.

Only then should we consider turning it into an actual trading strategy.
